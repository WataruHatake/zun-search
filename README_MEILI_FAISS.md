# Zun Search — Meilisearch＋FAISS版

現在のアプリはMeilisearch＋FAISS版に統一しました。起動・設定・CLIの手順は [README.md](README.md) を参照してください。

アプリ名は **Zun Search（ずんさーち）**。ブラウザのタブと画面左上に、枝豆モチーフのアイコンを表示します。画像は組み込みのimagegenで新規生成したもので、公式のずんだもん画像ではありません。画像と生成プロンプトは [assets/](assets/) に保存しています。

専用起動コマンドでは、深めの枝豆色のアクセントと薄い緑の背景を使います。画面上部と質問ウィンドウにはずんだもんの立ち絵を添え、案内文を「なのだ」口調にしています。検索・資料更新・回答・評価の処理中だけ枝豆アイコンがゆっくり揺れます。端末の「動きを減らす」設定では静止します。資料に基づく回答本文の生成指示は変更していません。

立ち絵 `assets/zundamon.png` は、**坂本アヒルさん制作の[ずんだもん立ち絵素材V3.2](https://seiga.nicovideo.jp/seiga/im11206626)**を使用しています。[作者の配布ZIP](https://uu.getuploader.com/s_ahiru/download/59)にある「基本版.psd」の保存時の表示を、macOS標準の `sips` で透過PNGに書き出しました。元のポーズ・表情を使い、画面での表示サイズだけ調整しています。作者の同梱説明を [assets/zundamon-readme.txt](assets/zundamon-readme.txt) に保存しています。素材の利用は同説明と[キャラクター公式ガイドライン](https://zunko.jp/guideline.html)に従ってください。

立ち絵は1082×1594pxの元画像を配信し、コンテナの幅で画面上部96px・質問ウィンドウ64pxに表示します。`st.image` に直接小さい数値幅を指定すると配信画像まで縮小されるため、表示サイズと画像の解像度を分けています。

この変更後の検索・ページ移動・質問・回答リセットと、正常終了／エラー時の処理中表示の消去を回帰テストで確認しました（`output/test-zun-search-character.txt`）。ブラウザでも配色、立ち絵、処理中だけ2.4秒周期で揺れる枝豆と完了後の消去を確認しています。

検索結果の上下にページ移動ボタンがあります。「この資料に質問する →」を押すと画面中央に質問ウィンドウが開き、一覧の上部に戻る必要はありません。原本を開く・Finderで表示・本文確認も同じウィンドウで行えます。閉じると検索結果の閲覧に戻れます。

質問ウィンドウの「回答をリセット」で、表示中の回答と出典を消せます。質問文と選択中の資料は保持され、そのまま再度質問できます。

操作性変更は一時資料13件の回帰テストで、上下のページ同期・質問送信・別資料への切り替え・全件表示を確認しました（`output/test-zun-search-ui.txt`）。実際のブラウザでも、下部からのページ移動、質問ウィンドウの表示、閉じた後の閲覧位置を確認しています。

旧版の画面・起動処理・取り込み機能は削除しました。本文保存・抽出・差分更新の共通基盤と現在の保存データは維持しています。モデルの準備も現在の「設定」内で行えます。

## 検索方式

「拡張子で絞り込む」は `.pdf`・`.pptx`・`.xlsx`・`.md`・`.txt` の複数選択に対応します。選択したいずれかの形式を対象とし、候補の件数制限と本文判定の前に絞ります。明示選択をAIの形式解釈より優先し、未選択時はAI補完の検索文に形式指定があればその解釈を使います。絞り込みは保存済みメタデータと既存の検索索引を使うため、再ベクトル化は不要です。

| 方式 | 向いている場面 | 処理 |
|---|---|---|
| ハイブリッド検索（全文＋ベクトル） | 普段の検索 | MeilisearchとFAISSの候補順位を統合 |
| AIによる検索文補完＋ハイブリッド検索 | 曖昧な表現や、内容を判断して探したい場合 | 言い換えで候補を広げ、ローカルLLMが本文の関連性を判定して選別 |
| 全文検索（入力した言葉） | 資料にある言葉が分かる場合 | Meilisearchだけで検索。モデル不要 |

番号で選んでいた旧③はAI検索に置き換えました。検索方式は3種類のまま、「検索後の並べ替え」を別に表示します。ハイブリッド検索では「専用リランカーで並べ替える」をオン・オフできます（初期値はオフ）。オンにすると、検索済みの上位候補を設定中の専用モデルで並べ替え、対象外の候補は末尾に残します。全文検索は元の検索順位を使い、AI検索はLLMが並べ替え・絞り込みを行うため、専用リランカーを重ねません。結果には実際に使用したモデルを表示し、並べ替えに失敗した場合は警告付きで元の検索順位を表示します。

「検索を評価」では専用リランカーの有無や、比較用のLLMによる並べ替えを比較できます。通常検索のチェック項目は既存の `dedicated` 処理を使います。新しい依存ライブラリや、検索語・ファイル名ごとの特例は追加していません。

このMacでは、回答・意図解析・本文判定を、すでに導入されていた `qwen3.5:9b` に変更しました。4Bでは「話題についての資料を探す」と「その技術で資料を作る方法を探す」の取り違えが残ったためです。埋め込みモデルは `qwen3-embedding:4b` のままで、再ベクトル化は不要です。

AI検索は検索意図・求める資料形式・言い換え（最大2つ）をローカルLLMで読み取り、全文・ベクトルの上位候補を広く取得します。求める形式があれば、実ファイルの拡張子と照合してから本文を確認します。形式名の解釈はLLMに任せ、語ごとの別名辞書は使いません。

「本文の確認・並べ替えを行う資料数」（現在20）の上位資料について、取得済みの最大3箇所をまとめて読み、検索対象と必須条件を本文で満たすか、理由を出してから0〜3点で採点し、2点以上の資料だけを表示します。本文の主題と、組織名に検索語が偶然含まれるだけの一致を区別する指示です。特定の語や資料を除外する辞書ではありません。この資料数は専用リランカーで並べ替える上限にも使います。

結果にはAIの判定理由を表示し、「検索の内訳」でAIが読み取った意図・資料形式、全文・ベクトルそれぞれの候補数、本文確認を行った資料数を確認できます。ベクトル検索が0件ならその旨を表示します。AIの本文確認が失敗した場合は未確認の資料を出さず、再試行かハイブリッド検索を案内します。

AI検索では、上位候補を確保するためベクトル類似度の下限を0にしてから本文で採否を判断します。保存済みの下限0.7は変更しておらず、ハイブリッド・比較検索と資料への質問に適用します。AI検索は本文確認に時間がかかり、取得候補の上限外の資料や、確認した3箇所以外にある根拠を見落とす可能性があります。拡張子は候補の件数制限前に適用し、指定形式の中から候補を集めます。意図と関連性はAIが判定するため誤りは残り、抜粋との照合が必要です。

本文判定中はOllamaの `keep_alive` で同じモデルを保持し、少数資料を確認するたびに読み直す処理を省きます。最終組の判定後に解放し、途中で失敗した場合も保持期限は2分です。ほかのモデルを一括停止する処理は削除しました。[Ollamaのモデル保持設定](https://docs.ollama.com/api/chat)

## 起動

このMacでは依存関係を導入済みです。`start.command`をダブルクリックするか、プロジェクト内で次を実行します。

```sh
./start.command
```

専用Meilisearch（127.0.0.1:7701）と画面（8502）が起動します。Ollama（11434）が停止中なら、インストール済みアプリ内のCLIを優先し、`ollama serve` で起動します。チャット画面は開きません。起動ログは `.rag/meili-faiss/ollama.log` です。終了は起動したターミナルでControl+C。起動処理が立ち上げたサーバーだけを停止し、すでに実行中だったOllamaは停止しません。従来の `start_meili_faiss.command` も同じ画面を起動します。

macOSでは専用起動コマンドがFAISSとPyTorchのOpenMPライブラリを一本化します。専用リランカーとの併用時のクラッシュを防ぐため、画面の起動にはこのコマンドを使ってください。[関連するPyTorchの報告](https://github.com/pytorch/pytorch/issues/149201)

別のMacでは次の手順で依存関係を導入してください。

```sh
brew install meilisearch
./setup.command
```

## 資料の取り込みと更新

- **資料を読み込み・更新**：原本との内容差分を確認します。変更のない資料は本文抽出・ベクトル化を省きます。ファイル名や更新日時だけに依存せず、内容ハッシュを使います。
- **検索索引を作成・修復**：保存データからMeilisearchとFAISSの索引を再作成します。外部索引の更新が中断した場合も使えます。未完了の埋め込みは「資料を読み込み・更新」で再開します。

現在の保存先は `.rag/meili-faiss/` です。既存の資料・埋め込みを引き続き使用し、再読み込みは不要です。

## 比較するときの注意

- Meilisearchには既存のSudachiによる分かち書きを渡し、ファイル名・フォルダ名・形式・本文を検索します。形式には拡張子だけを保存し、全文検索の語として扱います。タイプミス許容は無効、入力は先頭10語までです。`matchingStrategy: all` を指定し、検索語の一部を勝手に落とさないようにしました。[検索語の一致方針](https://www.meilisearch.com/docs/capabilities/full_text_search/how_to/use_matching_strategy)
- 「ローカルAI」と「ローカル AI」などの表記違いを重複検索しません。全文検索へ実際に渡す語の組み合わせでも重複を除くため、同じ検索の繰り返しで加点が増えません。単語境界や記号が異なる「nowhere / now here」「C++ / C#」は別の検索文として保持します。
- 選択した1資料への質問では、Meilisearchの従来の `matchingStrategy: last` を維持します。質問中の「どう」「誰」などが本文になくても根拠候補を拾い、回答時に引用を検証します。
- AI検索とLLM比較では各資料の取得済み本文を最大3箇所、専用リランカーでは最上位1箇所を採点します。採用した資料のほかの取得箇所も結果に残します。専用リランカーとLLM比較は未採点・低得点の資料も残すため、AI検索とは表示件数と採否が異なります。
- FAISSは正規化済みベクトルの内積でコサイン類似度を計算します。正確な全件検索で、近似検索ではありません。全資料の検索では1ファイルにつき最大3箇所を取得します。[FAISSの索引一覧](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)
- 資料に変更があれば、MeilisearchとFAISSの索引全体を作り直す簡単な構成です。変更なしなら再作成しません。索引の再作成と、モデルによる再ベクトル化は別の処理です。大量の資料でこの再作成が遅くなった段階で、索引への差分反映を検討します。
- SQLiteは原文・出典・ベクトルの保管に引き続き使用します。共通の更新処理が作るFTS5表も残りますが、現在の全文検索には使用しません。
- 更新中の索引を検索しないよう、フォルダ単位で同時操作を制限しています。索引更新失敗時はエラーを表示し、修復完了まで検索を止めます。

## 検証

### 画像・Excel／PowerPointの図形（2026-09-11）

PNG・JPEG・WebPを検索対象に加えました。既存のOllamaの画像入力を使い、画像内の文字と図・写真の説明を文字列にして、既存のMeilisearch・FAISSへ渡します。新しいモデルやOCRサーバーは追加していません。現在の `qwen3.5:9b` と初期設定の `qwen3.5:4b` の画像入力対応を、ローカルの `/api/show` で確認しました。[Ollamaの画像入力仕様](https://docs.ollama.com/capabilities/vision)

Excelはセルの読み取りを維持したまま、シートのDrawingMLに保存された図形・テキストボックスの文字と画像を追加で読みます。出典にはシート名と配置セル付近を残します。PowerPointは既存のテキスト・図形・グループ・表に加えて画像とSmartArtの文字を読みます。両形式のグラフは、保存済みデータの点番号で項目・値を対応付け、表示形式も残します。OLEの本体・VML・外部リンク・図形間の位置や矢印の関係は今回の対象外です。

画像の結果は内容ハッシュとモデルの版・読み取り処理の版で識別し、同じ索引のSQLiteのmeta表へ保存します。重複画像・ファイル移動・再起動後も再利用します。画像解析に失敗しても同じOffice資料のテキストは残し、次回更新で失敗分を再試行します。モデルが画像非対応など、更新開始前のエラーでは既存の検索索引を無効にしません。画像処理の有効・無効を設定画面で変更でき、CLIでは `--no-images` でも省略できます。

実モデルでは既存の表の画像と枝豆イラストを別索引で検証しました。表の開発費1,800,000円・検証費240,000円・合計2,040,000円と担当者を取得し、イラストを「豆のさやに3粒の豆」と説明しました。画像内文字と図の説明はそれぞれAI読み取り・AI推定と表示します。細かい文字・誤認・説明の過不足は残り、長辺2048pxに縮小して処理します。初回は画像2件の解析とベクトル化で53.07秒、2回目は画像解析・ベクトル化とも0件でした（`output/image-validation.json`）。この2例による確認であり、画像全般の認識精度や本番機の速度を保証するものではありません。

Meilisearchで「音声認識 費用」から表の画像、「イラスト」から枝豆の画像を取得しました。「豆が三つ入ったさやの絵」はAIによる検索文補完＋ハイブリッド検索で枝豆の画像を取得しています（`output/image-search-validation.json`）。画像を再解析せず保存済み文章を検索する流れです。

回答の引用で離れた2行をモデルが連結する例も確認しました。各行が元の本文と一致する場合だけ別々の引用に分け、1行でも数値・文字が違えば回答を棄却します。生成指示でも連続した引用を求めています。`original_quote` の一箇所の照合条件は変更していません。画像由来の出典を「原文」と誤認させないよう、画面の見出しは「引用」にしました。記録は `output/image-answer-trace.json`、`output/image-answer-verified.json` です。

全43テストが通過しました（`output/test-image-objects-all.txt`）。グループ内テキストと画像、セル付近の出典、グラフの項目・値・表示形式、SmartArtの文字、外部リンクの未取得、画像キャッシュと再試行、設定画面からの更新、改ざんされた引用の棄却を確認しています。既存150資料の索引は再作成せず、アプリも停止した状態を維持しています。次回の通常更新で画像とOfficeの新しい読み取り処理を適用します。

### Ollamaの画面抑制・Excel（2026-09-11）

Ollamaのチャット画面を開いていた `open -g -a Ollama` を廃止しました。実行中サーバーの再利用と、停止中の `ollama serve` 起動・終了をテストしています。共有サーバーを停止せず、別ポート11435で同梱CLI 0.33.2の起動、API応答、検証用プロセスの終了も確認しました（`output/excel-validation/ollama-headless.json`）。

既存の150資料にはExcelが5件ありました。5件とも抽出でき、うちデモの `PJ費用.xlsx` は合計セルの保存済み計算結果がないため警告します。タイトルが1行目にある表では各行に列見出しが付かない問題を修正しました。最初の複数セル行を見出しとする簡単な処理です。多段見出し・同じシート内の複数表・縦方向の結合セルの文脈は完全には解析しません。数値にはExcelの表示形式を添え、割合や桁区切りの意味を保持します。数式再計算やグラフの意味理解には未対応です。

検証用の架空Excelを `outputs/01a08545-50cb-7ce2-815d-fcc94b033ea9/Excel検索検証.xlsx` に作成しました。費用・日程・在庫の3シートで、数式の保存値204万円、日付、87.5%、品番文字列007、在庫0を確認しています。原本と現在の150資料の索引は変更していません。既存のExcelへの変更適用は次回の通常更新時です。Excel専用の抽出版数により、変更のない他形式の資料の再抽出・再ベクトル化を避けます。

この検証用Excelと既存Excel2件のコピーを別索引（3資料・30ベクトル）に取り込み、6検索文を全文・ハイブリッド検索で確認しました。12件とも正解資料が1位、または意図した0件でした。ただし現在の類似度下限0.7では全件でベクトル候補が0件になり、結果は全文検索によるものです。下限を外した診断では、正解がある5検索のFAISS単独1位は4件正解、残る「青空商事 費用」は別会社の費用表でした。全形式の取りこぼしと誤検出を比較せずに、下限を一律に下げてはいません。

最終版の `qwen3.5:9b` では、開発費180万円と担当者、合計204万円、予定日と87.5%、品番007と在庫0の4問で、値と出典が一致しました。資料にない2027年の売上は回答しませんでした。各問約2〜16秒です。在庫の回答文には閉じ括弧の欠落が残り、文章表記まで完全ではありません。少数の作例による確認であり、Excel全般の精度を保証する評価ではありません。
